СТАНДАРТЫ ОФОРМЛЕНИЯ ТЕСТ-КЕЙСОВ КОМПАНИИ

### 1. Идентификация и метаданные

#### `id`

Рекомендуемый формат:

```text
TC-{PROJECT}-{DOMAIN}-{NNNN}
```

Пример:

```text
TC-PAY-REFUND-0042
```

Правила:

- идентификатор уникален глобально в пределах тестовой системы;
- после создания теста `id` не изменяется;
- номер не переиспользуется после удаления;
- при переносе теста между проектами сохраняется исходный идентификатор;
- дубликаты запрещены;
- идентификатор не должен зависеть от номера задачи или позиции теста в списке.

Если компания не готова вводить составной идентификатор, минимальный вариант:

```text
TC-NNNN
```

где используется минимум четыре цифры.

#### Обязательные метаданные

| Поле | Обязательное | Правило |
|---|---:|---|
| `id` | Да | Уникальный неизменяемый идентификатор |
| `title` | Да | Кратко описывает проверяемое поведение |
| `status` | Да | `Draft`, `Ready`, `Approved`, `Deprecated`, `Archived` |
| `owner` | Да | Ответственный за актуальность теста |
| `component` | Да | Компонент, сервис или функциональный модуль |
| `priority` | Да | Определяется риском |
| `test_types` | Да | Список из одного или нескольких типов |
| `requirement_ids` | Да | Одна или более ссылок на требования |
| `created_at` | Да | Дата создания |
| `updated_at` | Да | Дата последнего изменения |
| `reviewed_at` | Для `Approved` | Дата последнего review |

### 2. Название и описание

#### `title`

Вместо жёсткого требования «начинается с глагола» лучше использовать шаблон:

```text
[Объект] — [условие или действие] — [ожидаемое поведение]
```

Примеры:

```text
Заказ — отменить после оплаты — статус меняется на «Отменён»
Платёж — ввести просроченную карту — отображается ошибка валидации
Отчёт — экспортировать 100 000 записей — файл формируется не более чем за 30 секунд
```

Правила:

- не более 120 символов;
- название должно быть уникальным в пределах компонента;
- запрещены названия `Проверить оплату`, `Тест авторизации`, `Проверка работы формы`;
- не следует указывать в названии конкретный номер сборки, если он не является частью сценария;
- название должно позволять понять цель теста без открытия остальных полей.

Ограничение в 80 символов можно оставить для интерфейса, но лучше не делать его обязательным: иногда оно приводит к потере значимой части сценария.

#### `description`

Вместо минимального количества слов следует определить обязательную структуру:

```text
Проверяется: <объект или функция>.
Условия: <важные предусловия и ограничения>.
Ожидается: <проверяемое поведение или бизнес-результат>.
```

Пример:

```text
Проверяется отмена оплаченного заказа пользователем с ролью клиента.
Условия: заказ находится в статусе «Оплачен», срок отмены не истёк.
Ожидается: заказ переходит в статус «Отменён», а пользователю
отображается подтверждение операции.
```

Описание не должно дублировать все шаги. Его назначение — дать контекст и обозначить цель теста.

### 3. Структура выполнения теста

Минимальный состав тест-кейса следует расширить:

```yaml
id: TC-PAY-REFUND-0042
title: "Заказ — отменить после оплаты — статус меняется на «Отменён»"
description: |
  Проверяется отмена оплаченного заказа пользователем с ролью клиента.
  Условия: заказ находится в статусе «Оплачен», срок отмены не истёк.
  Ожидается: заказ переходит в статус «Отменён».
preconditions:
  - "Пользователь авторизован с ролью «Клиент»"
  - "Существует оплаченный заказ без активной доставки"
test_data:
  order_id: "создаётся через API"
  user_role: "customer"
environment:
  application: "web"
  browser: "Chrome"
  build: "определяется при выполнении"
steps:
  - action: "Открыть раздел «Мои заказы»"
    expected_result: "Отображается список заказов пользователя"
  - action: "Открыть оплаченный заказ"
    expected_result: "Отображается карточка заказа со статусом «Оплачен»"
  - action: "Нажать «Отменить заказ» и подтвердить операцию"
    expected_result: "Заказ получает статус «Отменён»"
postconditions:
  - "Заказ не доступен для повторной отмены"
```

#### `preconditions`

Обязательное поле, если тест зависит от состояния системы.

Хорошие предусловия:

- проверяемые;
- конкретные;
- минимальные;
- не дублируют шаги;
- не требуют скрытых действий.

Плохо:

```text
Пользователь подготовлен.
```

Хорошо:

```text
Пользователь авторизован с ролью «Менеджер», а заказ находится в статусе «Новый».
```

#### `test_data`

Не следует помещать критичные данные непосредственно в шаги. Нужно указать:

- источник данных;
- формат;
- способ создания;
- допустимость повторного использования;
- требования к маскированию;
- способ очистки.

Секреты, реальные пароли и персональные данные в тест-кейсах запрещены.

#### `steps`

Лучше разделять шаг на:

- `action` — одно действие;
- `test_data` — данные для действия;
- `expected_result` — локальный результат этого действия.

Требования:

- один шаг содержит одну логически завершённую операцию;
- шаг должен быть воспроизводимым другим тестировщиком;
- нельзя использовать неформальные действия: «проверить», «убедиться», «работать с формой»;
- нельзя скрывать несколько действий в одном шаге, если между ними есть отдельная проверка;
- шаги должны быть независимы от текущего состояния интерфейса, если это состояние не является частью сценария.

### 4. Ожидаемые результаты

Общий `expected_result` следует заменить на обязательный ожидаемый результат для каждого шага и, при необходимости, на итоговый результат теста.

Каждый результат должен быть:

- наблюдаемым;
- однозначным;
- проверяемым;
- привязанным к конкретному объекту;
- измеримым, если речь идёт о времени, количестве или размере;
- независимым от субъективной оценки тестировщика.

Запрещённые формулировки:

```text
Система работает корректно.
Всё отображается правильно.
Должно работать.
Ошибок нет.
Как ожидается.
```

Улучшенные формулировки:

```text
Поле «Сумма» подсвечивается красным цветом, а под ним отображается сообщение
«Сумма должна быть больше 0».
```

```text
HTTP-ответ имеет код 422, поле `error_code` содержит значение `INVALID_AMOUNT`,
а платёж не создаётся.
```

```text
После подтверждения операции статус заказа изменяется с `PAID` на `CANCELLED`
в UI и в API-ответе.
```

### 5. Приоритет, тип и риск

#### `priority`

Оставить значения можно, но определить их через влияние:

| Приоритет | Критерий |
|---|---|
| `Critical` | Отказ блокирует основной бизнес-процесс, приводит к потере данных или нарушению безопасности |
| `High` | Существенно нарушается важная функция, есть значимый финансовый или пользовательский эффект |
| `Medium` | Функция работает с ограничениями, но есть обходной путь |
| `Low` | Незначительное отклонение, косметический дефект или редкий сценарий |

Дополнительно полезно хранить:

```yaml
risk:
  business_impact: high
  failure_probability: medium
  detectability: medium
  score: 6
```

Правило «20% тестов должны быть High+» лучше удалить и заменить контролем:

- все Critical-тесты входят в обязательный smoke/regression-набор;
- все требования с критичным риском имеют покрытие;
- для каждого релиза выполнены все тесты, необходимые по risk-based scope;
- отсутствие обязательного теста блокирует релиз независимо от процентной нормы.

#### `type`

`type` должен быть массивом, а не одним значением:

```yaml
test_types:
  - Functional
  - Negative
  - Boundary
```

Рекомендуемый справочник:

```text
Functional
Negative
Boundary
Integration
API
UI
E2E
Regression
Smoke
Security
Performance
Compatibility
Accessibility
Recovery
Migration
Contract
```

Тип описывает **характер проверки**, а не её приоритет или статус выполнения.

## Дополнительные проверки качества

В стандарт следует добавить автоматизируемый quality gate для тест-кейсов:

```text
Тест-кейс может получить статус Ready, если:

- заполнены все обязательные поля;
- есть ссылка хотя бы на одно требование;
- определены предусловия или явно указано, что они не нужны;
- указаны тестовые данные или источник их получения;
- каждый шаг атомарен;
- каждый шаг имеет ожидаемый результат;
- нет запрещённых формулировок;
- выбран хотя бы один test type;
- priority обоснован risk-полями;
- тест не является дубликатом;
- тест прошёл peer review;
- отсутствуют секреты и реальные персональные данные.
```

Для автоматической проверки можно использовать такие правила:

```python
def validate_test_case(test_case: dict) -> list[str]:
    errors = []

    if not test_case.get("id", "").startswith("TC-"):
        errors.append("Некорректный идентификатор")

    if not test_case.get("title"):
        errors.append("Не заполнено название")

    if len(test_case.get("title", "")) > 120:
        errors.append("Название длиннее 120 символов")

    if not test_case.get("requirement_ids"):
        errors.append("Нет связи с требованиями")

    if not test_case.get("test_types"):
        errors.append("Не указан тип теста")

    for index, step in enumerate(test_case.get("steps", []), start=1):
        if not step.get("action"):
            errors.append(f"Шаг {index}: отсутствует действие")
        if not step.get("expected_result"):
            errors.append(f"Шаг {index}: отсутствует ожидаемый результат")

    forbidden = (
        "должно работать",
        "как ожидается",
        "всё ок",
        "система работает корректно"
    )

    text = str(test_case).lower()
    for phrase in forbidden:
        if phrase in text:
            errors.append(f"Использована запрещённая формулировка: {phrase}")

    return errors
```

## Рекомендуемый итоговый шаблон

```yaml
id: TC-{PROJECT}-{DOMAIN}-{NNNN}

title: "<объект> — <условие или действие> — <ожидаемое поведение>"

description: |
  Проверяется: <объект или функция>.
  Условия: <контекст и ограничения>.
  Ожидается: <проверяемый бизнес- или системный результат>.

requirement_ids:
  - REQ-123

risk:
  business_impact: Medium
  failure_probability: Medium
  detectability: Medium
  score: 4

priority: Medium

test_types:
  - Functional
  - Negative

component: "<сервис или модуль>"
owner: "<ответственный>"
status: Draft

preconditions:
  - "<проверяемое предусловие>"

test_data:
  - name: "<название набора данных>"
    source: "<fixture/API/SQL/manual>"
    cleanup: "<способ очистки>"

environment:
  application: "<приложение>"
  platform: "<платформа>"
  browser: "<браузер, если применимо>"
  build: "<версия при выполнении>"

steps:
  - number: 1
    action: "<одно атомарное действие>"
    test_data: "<данные>"
    expected_result: "<конкретный проверяемый результат>"

postconditions:
  - "<состояние системы после выполнения>"

automation:
  status: Manual
  repository: null
  test_path: null

review:
  reviewer: null
  reviewed_at: null
  design_techniques:
    - Equivalence Partitioning
    - Boundary Value Analysis
```
